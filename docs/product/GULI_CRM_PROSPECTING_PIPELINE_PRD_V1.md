# GuliCRM 获客与商机闭环 PRD V1

状态：实施草案；2026-10-21 基于当前 `gulierp-next` 源码和本地测试环境核对。产品总称为 **Guli Platform**，GuliCRM 与 GuliERP 平级。本文只规划 CRM 获客流程，不改变已确认的 CRM Company 与 ERP BusinessPartner 分域边界。

## 1. 目标和结论

为三人销售团队建立一条可追溯的工作路径：**情报信号 / 站点采集 / 单位清单 → 身份核验与去重 → 多业务需求初评 → 人工确认 → 线索与客户 → 商机 → 获客准备包 → 联系与跟进 → 报价**。每个建议都应能回答“依据是什么、何时取得、谁确认、下一步由谁在何时完成”。试点以销售团队能否每日使用、数据能否核验和回溯为验收标准，不以自动生成内容的数量或成交量替代软件验收。

**产品决策**：GuliCRM 是企业资料、证据、评估、商机阶段、报告版本与跟进承诺的主记录系统。规则引擎负责可解释的初筛；MiniMax、豆包、WorkBuddy 等外部工具可以作为可替换的研究或文案执行器，输入经授权的最小资料，输出结构化草稿并回写待审核记录。Codex 主要用于软件开发、数据处理和经授权的本地工作流，不作为 CRM 运行时唯一依赖。任何 AI 结论不得自动变成“客户已确认需求”；发送消息、公开报告和正式报价仍须人工审定。

**产品边界补充**：CRM 的“线索池”保留为销售跟进记录；规划中的 Guli Lead 是平台级跨来源发现、核验与候选线索治理产品，确认后向 CRM 输送。Guli GEO 是平台级 AI 可见性诊断与交付产品，其诊断结果可成为 CRM 需求评估证据。第一列暂显示两者禁用占位，不表示已有独立系统、数据表或权限。当前商机建议仅对有规则依据的方向生成“待核验”假设；官网字段缺失不等于企业无官网，自媒体与外贸获客在证据规则落实前不自动推断。

## 3. 用户与边界

| 角色 | 可执行动作 | 边界 |
| --- | --- | --- |
| 销售人员 | 查看有权范围内的信号、线索、客户、建议与商机；采集、补全、提出评估草稿、记录跟进 | 不能查看密钥明文；不能把“未查询到”改写为“确认不存在” |
| 销售负责人 | 确认需求方向、优先级、负责人、报告和触达话术 | 需记录确认人、时间、证据与修改原因 |
| 公司管理员 | 配置当前公司可用的采集连接与角色 | 凭据只保存在服务端；配置状态可见，密钥不可读回 |
| 外部 AI 执行器 | 按任务读取最小授权输入，生成带来源的草稿 | 不直接修改客户事实、商机结果，不自动发送 |

数据仍按租户和公司隔离。外部站点、联系人与联系方式必须保留来源、采集时间和核验状态；凭据不进入前端持久存储、日志、源码、导出文件或报告。

## 4. 业务流程与页面契约

| 步骤 | 当前资产 | 目标动作与输出 | 必须避免的误判 |
| --- | --- | --- | --- |
| 1 情报信号 | `SignalCenter` 有列表、状态、证据与核验入口 | 记录来源、原始证据、事件时间、可信度、核验人；确认后关联线索/客户 | “未查到”不等于“已证实不存在” |
| 2 站点采集 | Quake 搜索、冷却历史、ICP/网站/GEO 检测和批量导入 | 显示连接状态、额度/查询结果与失败原因；先筛选、核验、去重，再导入 | 域名/IP 不自动等于目标企业 |
| 3 单位反查 | 上传清单、手工输入、ICP/网站/GEO 反查 | 保留每条输入、查询结果、来源和导入决定；未识别官网时保留未知状态 | “未找到网站”不等于“企业无官网” |
| 4 需求初评 | 实时商机建议规则 | 对建站、GEO、自媒体、外贸获客分别给出“未知/待核验/可能/已确认/不适用”、证据、置信度、建议动作 | 行业或来源只能形成假设，不能直接证明购买意愿 |
| 5 商机确认 | 客户主档、商机管理 | 只有人工确认客户与需求后创建正式商机；关联评估版本、负责人、下一步日期 | 不把线索建议自动等同已确认商机 |
| 6 获客准备 | 目前无统一准备包 | 生成可审核的企业画像、问题证据、诊断报告、破冰话题、异议应对、展示站点链接与触达计划 | 草稿不直接对外发送；演示站点需标明样例属性 |
| 7 跟进与报价 | 跟进记录可用，CRM 报价单未实现 | 每次联系回写结果和下次动作；在报价规范落地后从已确认商机生成报价 | 不把 ERP 销售订单当成 CRM 报价单 |

### 4.1 需求评估字段

四类需求均独立评估，允许多选；不以单一“AI 评分”代替。每项记录：`category`、`state`、`evidence[]`（类型/链接/采集时间/核验状态）、`reason`、`confidence`、`reviewer`、`reviewedAt`、`nextAction`、`version`。

2026-10-21 实施进度：单位反查已按公司自动保存每条查询快照（含失败和未知），页面提供最近 100 条历史；导入线索仍需销售手动点击。无输入网址时不得推定无官网，ICP 未查到不得写为“未备案”，备案企业名称不得自动覆盖输入单位。当前反查建议只属于待核验提示。

2026-10-22 业务确认：四类需求评估在 **CRM 线索创建后**保存；未导入的反查结果只保留查询证据。四类独立评估记录状态、置信度、证据、理由、下一步、审核人及版本号，且支持线索关联来源反查记录。“可能／已确认”必须填写证据。每次保存追加不可直接编辑的历史快照，旧评估迁移时回填当前快照。**所有新建正式商机必须从已确认的线索需求评估发起**；服务端核对客户、评估状态、当前版本和品类，并防止同一评估重复建商机。既有历史商机保留，不自动改写；原有独立创建入口引导销售回到线索需求评估。

- **建站**：是否有可核验官网、可访问性、HTTPS、移动端、内容时效、转化入口；“无官网”必须区分“未找到”和“确认没有”。
- **GEO**：品牌及产品在目标问答场景的可见性、可引用内容、结构化信息、竞品差距；已有域名或低分只表示评估线索。
- **自媒体**：已运营渠道、内容频率、素材能力、目标受众、线索承接；缺数据时不自动判为缺失。
- **外贸获客**：目标市场、语言站点、出口或海外渠道证据、询盘承接；国内经营范围或英文域名不能单独证明外贸需求。

### 4.2 AI 工具接入方式

系统提供统一任务契约：输入字段白名单、任务目的、允许的供应商、数据保留策略、输出 JSON Schema、引用来源、失败状态、费用/调用量、人工审核结果。先支持**人工复制或导入草稿**，再接入经验证的服务端 API；供应商不写入核心表结构。MiniMax、豆包、WorkBuddy 等分别作为候选执行器评估实际 API、授权、价格和数据协议。Codex 负责工程和本地辅助分析。最终展示统一由 CRM 页面完成，避免客户资料散落在各工具的会话中。

## 5. 分期实施与验收

| 阶段 | 任务 | 验收条件 | 粗估 |
| --- | --- | --- | --- |
| A 配置与可用性（本轮启动） | Quake 配置状态；管理员在服务端设置仅当前进程有效的测试密钥；无密钥时阻止无效搜索并给出路径；修复信号/商机状态枚举显示 | 密钥不回显、不进日志或仓库；普通 CRM 操作员不能设密钥；当前公司内搜索前可见配置状态；自动测试通过 | 1–2 人日 |
| B 证据与评估 | 持久化采集批次、身份匹配、证据和四类需求评估；规则版本与人工确认；建议关联线索/客户 | 一条建议可追溯来源与核验状态；重复查询和重复企业不生成重复客户；未知与否定区分 | 4–7 人日 |
| C 商机与准备包 | 扩展自媒体/外贸业务品类；评估→商机的人审入口；报告版本、破冰、异议、展示站点及触达计划 | 每个正式商机关联已确认客户、需求、负责人、下一步日期和可审核准备包 | 5–8 人日 |
| D 外部 AI 与报价 | 供应商适配器、结构化草稿回写、审批和费用监控；CRM 报价单对接统一 Business Document 规范 | 外部调用失败可重试且不丢证据；人工审批后才对外使用；CRM 报价与 ERP 销售订单边界清楚 | 6–10 人日，依 API 与报价范围调整 |

阶段 A 的运行时密钥是**本地开发与验收过渡能力**：保存在 API 进程内，重启需重填，多实例不共享。生产级密钥配置应在 B 阶段引入受保护的持久凭据存储、轮换和审计，不能把明文写入 PostgreSQL 或浏览器缓存。没有真实 Quake 密钥时，只验收配置保护、缺钥提示和模拟响应；不宣称真实采集通过。

## 6. 测试数据与停止条件

现有 18 条线索仅作为测试库业务样本，不自动批量采集或外发。下一轮用其中 2–3 条覆盖“有网站/无网站待核实/单位反查”；任何外部 API 调用须先确认密钥来源、费用、数据去向和查询额度。验收需区分：页面可见、接口授权、模拟服务、真实 Quake/ICP/GEO 返回、实库写入及人工业务判断。若服务端密钥存储、数据来源或审批规则尚未明确，停在草稿和模拟验证，不推进自动发布或发送。
